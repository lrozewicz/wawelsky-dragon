## 2. Moduł M10 — metadane (E6-1)

**Źródło prawdy**: upstream v0.27.2 `common/metadata_utils.py` (`apply_meta_data_filter`, `meta_filter`, `update_metadata_to`, `metadata_schema`/`turn2jsonschema`), `rag/prompts/generator.py` (`gen_metadata`, `gen_meta_filter`), `rag/svr/task_executor.py` (~550–590, krok auto-metadanych), `api/apps/restful_apis/{dataset_api,document_api,chunk_api,chat_api}.py`.

1. **Auto-metadane przy parsowaniu**: gdy `parser_config.enable_metadata` i niepusta konfiguracja pól — krok w handlerze `parse_document` po chunkowaniu, przed embeddingami: `gen_metadata` przez `LLMGateway` (model czatu datasetu/tenanta), wynik scalany do `documents.meta_fields` jak upstream (`update_metadata_to`), z cache LLM (M4). Błąd modelu ≠ porażka parsowania (log w zadaniu, jak upstream). Postęp zadania: osobny etap w logu zadania.
2. **`meta_data_filter`** w czacie (`chats.meta_data_filter`), Search (`search_config.meta_data_filter`) i `/retrieval` (`meta_data_filter`, gdy brak `metadata_condition` — reguła upstream `chunk_api.py:391`): metody `manual` (warunki), `auto` (warunki z LLM `gen_meta_filter` z listy metadanych datasetów), `semi_auto` (LLM tylko po wybranych kluczach). Pusty wynik filtra w `auto`/`semi_auto` → zachowanie upstream (fallback opisany w docstringu `apply_meta_data_filter`).
3. `metadata_condition` na `GET …/documents` **zawęża** wynik (dziś tylko walidacja); trasa `PUT …/documents/{id}/metadata/config` (zdejmuje S-320).
4. Wydajność: filtr liczony w Pythonie na `meta_fields` dokumentów datasetów — próg: **10 000 dokumentów, filtr ≤ 200 ms** (pomiar w E6-1a; przekroczenie → pushdown `JSON_EXTRACT` dla `manual`, decyzja Doradcy z DEC).
5. **UI** (08-frontend): w Konfiguracji datasetu — edytor pól metadanych (nazwa, typ, opis, wartości dozwolone) + przełącznik „Auto-metadane”; w zakładce dokumentów — kolumna/drawer metadanych z edycją; w szufladzie ustawień czatu i Search — sekcja „Filtr metadanych” (manual: kreator warunków; auto; semi_auto: wybór kluczy); w teście retrievalu — filtr manualny. Scenariusz e2e **S6-15**.
6. fake-llm: deterministyczne odpowiedzi JSON dla promptów `gen_metadata` i `gen_meta_filter` (rozpoznanie po szablonie promptu — K10 poprawka w WP).

## 3. Moduł M11 — serwer MCP (E6-2)

**Źródło prawdy**: upstream v0.27.2 `mcp/server/server.py`, `mcp/client/*`, `docker/docker-compose.yml` (komentarz `--enable-mcpserver`).

1. Narzędzia **dokładnie jak upstream** (nazwy, opisy, `inputSchema`): `ragflow_retrieval`, `ragflow_list_datasets`, `ragflow_list_chats`. Złoto: lista narzędzi i odpowiedzi `call_tool` nagrane z upstream (E6-0).
2. Transporty: **streamable HTTP** (`/mcp`) i **SSE** (`/sse` + `/messages/`) — jak upstream. Autoryzacja: klucz API WD (`ragflow-…`) w `Authorization: Bearer` lub nagłówkach `api_key`/`X-API-Key` (tryb upstream `host`); tryb `self-host` z `WD_MCP_HOST_API_KEY` — opcjonalny.
3. Wdrożenie: usługa compose **`mcp`** (ten sam obraz `wawelsky/backend`, `python -m app.mcp`), **profil `mcp`** (domyślnie wyłączona — lekkość), port wewnętrzny 9382; publicznie **przez `web`** (proxy ścieżek `/mcp` i `/sse`, `/messages/`) — jedyny publiczny port 8080 bez zmian. Serwer woła **API WD po HTTP** (`http://api:8000/api/v1`) jak upstream — bez importu warstwy usług (izolacja, ten sam model uprawnień co klient REST).
4. Zależność: oficjalny pakiet `mcp` (wersja sprawdzona w PyPI przy WP; `pip-audit` czysty).
5. Testy: integracyjne klientem z pakietu `mcp` na stosie testowym (oba transporty, brak/zły klucz → błąd jak upstream), kontrakt narzędzi ze złotem. Bez UI (w Ustawieniach → Klucze API: jedna sekcja „MCP” z adresem i przykładem konfiguracji klienta).

## 4. Moduł M12 — prosty Agent bez canvas (E6-3)

**Źródło prawdy**: upstream v0.27.2 `api/apps/restful_apis/agent_api.py`, `agent/canvas.py`, `agent/component/{begin,agent_with_tools,message}.py`, `agent/tools/{retrieval,searxng,tavily,duckduckgo}.py`.

1. **API** (podzbiór `/api/v1`, kształt jak upstream): `GET/POST /agents`, `GET/PUT/DELETE /agents/{id}`, `GET/POST/DELETE /agents/{id}/sessions`, `GET/DELETE /agents/{id}/sessions/{sid}`, `POST /agents/chat/completions` (SSE i JSON jak upstream), `GET /agents/templates` (1–2 szablony WD). Pozostałe trasy `/agents*` (webhook, versions, debug, rerun, upload, test_db_connection, attachments) i `/agents_openai/*`, `/agentbots/*` — stub `NotSupported` jak dziś (K11 tabela odmów).
2. **DSL**: przyjmujemy i zwracamy format DSL upstream (JSON canvas), ale runtime obsługuje **wyłącznie graf liniowy `Begin → Agent → Message`**; komponent `Agent` z narzędziami `Retrieval` i web search (`SearXNG` domyślnie; `Tavily`, `DuckDuckGo`, `Google` z rejestru dostawców — tylko jeśli skonfigurowane). Inny komponent/narzędzie → błąd z kodem i komunikatem K3 („component X is not supported by Wawelsky Dragon”) przy zapisie i przy uruchomieniu. Agent zapisany w RAGFlow z nieobsługiwanymi komponentami **migruje się** (`ragflow_migrate`), ale jest oznaczony jako nieuruchamialny.
3. **Runtime**: pętla function-calling (OpenAI `tools`) przez `LLMGateway`, limit rund jak upstream (`max_rounds`), strumień SSE z ramkami jak upstream (`message`, `node_started/finished` w zakresie trzech węzłów, `message_end`), cytowania z narzędzia Retrieval w formacie czatu (K4). Koszt: tokeny w logu sesji.
4. **Web search**: interfejs `WebSearchProvider` + rejestr (Q19): `searxng` (domyślny), `tavily`, `brave`, `duckduckgo` — konfiguracja dostawcy w Ustawieniach (admin) i wybór per narzędzie agenta; klucze zewnętrznych dostawców szyfrowane jak klucze modeli (M4 crypto). Usługa compose **`searxng`** (obraz upstream SearXNG, wersja przypięta; konfiguracja JSON API w `docker/searxng/settings.yml`), w stosie testowym **stub `fake-searx`** (deterministyczne wyniki). Dostawcy zewnętrzni: testy jednostkowe na nagranych odpowiedziach, bez live (Q19).
5. **Dane**: migracja **0008** — `agents` (podzbiór kolumn upstream `user_canvas`: id, tenant_id, title, description, avatar, dsl JSON, canvas_category, permission, timestamps), `agent_sessions` (podzbiór `api_4_conversation`: id, agent_id, user_id, messages JSON, reference JSON, dsl snapshot, timestamps), `web_search_providers` (tenant, provider, config JSON zaszyfrowany). DDL zamrażany w K2 §6 przed WP.
6. **UI**: `/agents` (lista, tworzenie z szablonu), `/agent/:id` — **formularz** zamiast canvas: nazwa, opis, model, prompt systemowy, narzędzia (checkboxy: Retrieval + wybór datasetów i parametrów; web search + dostawca), limit rund; panel testowy rozmowy (komponenty Chat workspace). Flaga `FEATURE_AGENT` → domyślnie włączona. `@xyflow/react` **nie** wchodzi (brak canvas). Scenariusz e2e **S6-16**.
7. fake-llm: obsługa `tools`/`tool_calls` (deterministyczny scenariusz: wywołanie narzędzia → odpowiedź z wynikiem) — K10 poprawka.
8. **Live** (Q20): `tools/dev/live.sh pytest-live tests/live/agent/` — budżet **10 USD na E6**, szacunek kosztu w briefie, licznik tokenów w artefakcie.

## 8. Ryzyka
- DSL upstream jest szeroki — ryzyko „prawie zgodnego” Agenta: ograniczamy się do grafu liniowego i jawnie odrzucamy resztę (lepiej czytelna odmowa niż ciche złe działanie).
- SearXNG (AGPL-3.0) jako **osobny kontener** bez modyfikacji — nie wpływa na licencję WD (Q22); wyniki zależne od zewnętrznych wyszukiwarek → testy wyłącznie na stubie.
- fake-llm z `tool_calls` musi być deterministyczny, inaczej e2e S6-16 będzie niestabilny.
- Pakiet `mcp` szybko się zmienia — wersja przypięta, aktualizacje przez `pip-audit`.
